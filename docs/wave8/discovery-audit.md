### 1.2 Route A — `routes/web.php:10`

```php

    ->middleware('web');
```

**Middleware stack**: `web` (EncryptCookies, AddQueuedCookies, StartSession, ShareErrorsFromSession, ValidateCsrfToken, SubstituteBindings)

Laravel's route registration order means the service-provider registration overwrites the `web.php` definition. The `web.php` version is never reached.

### 1.3 Route B — `SanctumServiceProvider.php:72-76`

```php
Route::group(['prefix' => config('sanctum.prefix', 'sanctum')], function () {
    Route::get(
        '/csrf-cookie',
        CsrfCookieController::class.'@show'
    )->middleware('web')->name('sanctum.csrf-cookie');
});
```

**Middleware stack**: Same `web` group as Route A.

**Controller** (`vendor/laravel/sanctum/src/Http/Controllers/CsrfCookieController.php`):
```php
public function show(Request $request)
{
    if ($request->expectsJson()) {
        return new JsonResponse(status: 204);
    }
    return new Response(status: 204);
```

Returns an empty 204 response. The **middleware** does the actual work — `StartSession` creates/restores the session, `EncryptCookies` and `AddQueuedCookies` handle the `XSRF-TOKEN` cookie, and the session middleware triggers `SetCookie` for both `ecommerce_session` and `XSRF-TOKEN`.

**This is the production dependency**. All CSRF cookies are generated by this route.

### 1.4 Route C — `routes/api.php:287-288`

```php
Route::get('/sanctum/csrf-cookie', [CsrfOwnershipPreparationController::class, 'show'])
    ->middleware(['web', 'identity.route:shared_transitional,merchant,observe']);
```

**Full URI**: `GET /api/sanctum/csrf-cookie` (prefixed by `api` route group).

**Middleware stack**:
1. `api` group (throttle, bindings, etc.)
2. `web` group (cookies, session, CSRF)
3. `identity.route:shared_transitional,merchant,observe` (ApplyIdentityRouteContext)

**Controller** (`app/Http/Controllers/Api/Shared/Auth/Preparation/CsrfOwnershipPreparationController.php`):
```php
public function show(Request $request): Response
{
    $ownership = $this->sessionOwnershipResolver->resolveForCsrf($request);
    $shadow = $this->guardShadowAnalyzer->analyze($ownership);
    $this->sessionGuardTelemetry->logCsrfOwnership($request, $ownership, $shadow);

    $response = $this->csrfCookieController->show($request);
    $response->headers->set('X-Session-Auth-Domain', (string) $ownership->authDomain);
    $response->headers->set('X-Session-Route-Domain', (string) $ownership->routeDomain);
    $response->headers->set('X-Future-Guard-Hint', $shadow->futureGuardHint);

    return $response;
}
```

Delegates to the same `CsrfCookieController` after adding ownership resolution + telemetry + response headers.

**This controller is never called in production.** See Section 2 for why.

### 1.5 Why Both Routes B and C Exist

| Reason | Detail |
|---|---|
| **Route B is Sanctum's default** | `SanctumServiceProvider` auto-registers `GET /sanctum/csrf-cookie` with `web` middleware. Every Sanctum SPA app gets this. |
| **Route C is the custom ownership wrapper** | Added during Wave 4 CSRF ownership preparation to add domain telemetry headers. Registered under the `/api/` prefix to be inside the `api` middleware group. |
| **They coexist but Route C is unused** | Route B handles the default `sanctum/csrf-cookie` URI. Route C handles `api/sanctum/csrf-cookie`. They are **different URIs**, so no conflict. But the frontend only calls Route B's URI. |

### 1.6 Why Route C Exists Under `/api/`

The `api` prefix was chosen to place the preparation controller within the `api` middleware group, which includes rate-limiting and other API infrastructure. The `web` middleware is re-applied explicitly at the route level because Sanctum CSRF needs session support.

### 1.7 Which Consumer Hits Which Route

| Consumer | URI | Route | Production? |
|---|---|---|---|
| Nuxt frontend (Nitro proxy) | `{apiRoot}/sanctum/csrf-cookie` | **B** | **Yes** — every state-changing request without an XSRF-TOKEN cookie |
| Browser (direct fetch) | Never calls CSRF endpoint directly | N/A | No — Nitro proxies all backend calls |
| Apollo GraphQL | Never calls CSRF endpoint | N/A | No — relies on browser auto-sending cookies |
| Auth bootstrap (login/register) | No direct CSRF call | N/A | No — Nitro's `proxySessionAuthRequest` handles it |

### 2.2 CSRF Bootstrap Trigger Logic

`server/utils/api.ts:234-253`:

```typescript
const requiresCsrf = !['GET', 'HEAD', 'OPTIONS'].includes(method)

if (requiresCsrf && !getCookie(event, 'XSRF-TOKEN')) {
    const csrfResponse = await fetch(`${apiRoot}/sanctum/csrf-cookie`, {
        method: 'GET',
        headers,
    })
    // ...forward Set-Cookie headers to browser
}
```

**Key details**:
- CSRF bootstrap only fires for state-changing methods (POST, PUT, PATCH, DELETE)
- Only fires when no `XSRF-TOKEN` cookie exists in the request
- Calls `{apiRoot}/sanctum/csrf-cookie` where `apiRoot` is the bare origin (e.g., `http://localhost:8000`) — **no `/api/` prefix**
- The `headers` object at this point includes: `X-Tenant-Id`, `X-Storefront-Locale`, `X-Storefront-Version`, `Origin` (if present in browser request), `Accept-Language`, `Authorization` (if token exists), and `Cookie`

### 2.3 Which Endpoints Trigger CSRF Bootstrap

Only 5 Nitro endpoints use `proxySessionAuthRequest()` which includes CSRF bootstrap:
- `POST login`
- `POST register`
- `POST logout`
- `POST checkout/session`
- `POST checkout/session/auth`

The remaining 29+ Nitro endpoints (using `useServerApi` or direct fetch) **assume the XSRF-TOKEN cookie already exists** from a prior bootstrap. No CSRF call is made for GET/HEAD/OPTIONS requests.

### 2.4 Real Production Dependency

**The real production dependency is Route B** (`GET /sanctum/csrf-cookie` → `CsrfCookieController` with `web` middleware). Route C (`GET /api/sanctum/csrf-cookie` → `CsrfOwnershipPreparationController`) is **not called by any frontend code**. The custom preparation controller and all its ownership telemetry is dead code in production.

## Section 3 — Middleware Ownership Audit

### 3.1 `identity.route:shared_transitional,merchant,observe`

**Definition location**: `routes/api.php:287-288` on the CSRF endpoint and `routes/api.php:281` on the Stripe webhook group.

**Middleware class**: `App\Http\Middleware\ApplyIdentityRouteContext`

**Parameters**:
```
identity.route:{routeDomain},{ownerAuthDomain},{enforcementMode}
```
- `routeDomain = shared_transitional`
- `ownerAuthDomain = merchant` (default fallback)
- `enforcementMode = observe`

### 3.2 Full Execution Pipeline

When this middleware runs, it executes the following sequence (`ApplyIdentityRouteContext::handle()`, lines 42-114):

1. **Parse annotation** → `RouteDomainContext(shared_transitional, merchant, observe)`
2. **Enrich trace context** with route domain metadata
3. **Resolve identity** → `IdentityContextResolver::resolve($user)` (null for guests)
4. **Resolve session boundary** → `SessionBoundaryMetadataResolver::resolve()`
5. **Resolve session ownership** → `SessionOwnershipResolver::resolve()` (uses identity context + route domain — **not** `resolveForCsrf()`)
6. **Analyze guard shadow** → `GuardShadowAnalyzer::analyze()`
7. **Resolve guard** → `TransitionalGuardResolver::resolve()`
8. **Simulate guard split** → `GuardSplitSimulationService::simulate()`
9. **Enrich trace context** with ownership, shadow, and guard resolution
10. **Log telemetry**: `session.ownership_resolved`, `session.guard_shadow_resolved`, `session.contamination_signals`
11. **Set guard**: `Auth::shouldUse($guardResolution->guard)`
12. **Enforce session ownership** → `enforceSessionOwnership()` — but returns immediately for `SHARED_TRANSITIONAL` (see 3.3)
13. **Check identity/route match** → `matchesOwnership()` at line 100-112 — in `observe` mode, logs but does NOT throw on mismatch

### 3.3 Enforcement Mode — `observe`

The `observe` enforcement mode controls behavior at two points:

**Point 1 — `enforceSessionOwnership()` (line 154-194)**:
```php
private function enforceSessionOwnership(...): void
{
    // If the route domain is shared transitional, we don't enforce strict ownership yet
    if ($sessionOwnership->routeDomain === RouteDomainEnum::SHARED_TRANSITIONAL) {
        return;  // <-- SKIPS ALL ENFORCEMENT
    }
    // ... contamination detection, fallback rejection, throw
}
```

Two enforcement paths are skipped:
1. **Session contamination detection**: If `sessionAuthDomain !== authDomain`, normally throws `InvalidIdentityDomainAccessException`. Skipped for `SHARED_TRANSITIONAL`.
2. **Fallback guard rejection**: If `$guardResolution->isFallback` is true, normally throws. Skipped for `SHARED_TRANSITIONAL`.

**Point 2 — Actor-domain mismatch (line 100-112)**:
```php
if ($identityContext !== null && !$this->matchesOwnership($identityContext, $routeDomainContext)) {
    // ...telemetry...
    if ($routeDomainContext->enforcementMode === RouteDomainEnforcementModeEnum::ENFORCE) {
        throw new InvalidIdentityDomainAccessException(...);  // Only throws in ENFORCE mode
    }
}
```

In `observe` mode, actor-domain mismatches are logged but allowed.

### 3.6 What Breaks If `shared_transitional` Is Removed Today

| Component | Breakage | Root Cause |
|---|---|---|
| **CSRF endpoint** | 403 on every CSRF refresh | `enforceSessionOwnership()` at line 160 no longer returns early — contamination detection or fallback guard rejection throws |
| **Stripe webhooks** | 403 on every webhook | No session identity means fallback guard is `web`, `isFallback` is true, `enforceSessionOwnership` throws at line 192 |
| **Guest checkout CSRF** | 403 on checkout initiation | Guest has no `auth_domain` in session → contamination detection at line 165 throws |
| **Multi-tab users** | Random 403s | Merchant tab has `auth_domain=merchant`, customer tab's CSRF refresh triggers contamination detection |

**Bottom line**: `shared_transitional` cannot be removed until per-domain CSRF or a split cookie architecture exists. It protects two structurally inseparable use cases: (1) shared CSRF refresh from multiple domains, and (2) stateless webhook processing.

## Section 4 — Resolver Audit

### 4.1 `SessionOwnershipResolver::resolveForCsrf()` — Full Source

`app/Services/Auth/SessionOwnershipResolver.php:45-62`:

```php
public function resolveForCsrf(Request $request): SessionOwnershipContext
{
    $referer = (string) ($request->headers->get('referer') ?? $request->headers->get('origin') ?? '');
    $routeDomain = str_contains($referer, '/storefront/account') ? 'customer_account' : 'merchant_users';
    $authDomain = $routeDomain === 'customer_account' ? 'customer' : 'merchant';

    return new SessionOwnershipContext(
        authDomain: $authDomain,
        actorType: null,
        routeDomain: $routeDomain,
        sessionOrigin: $request->hasSession() ? 'guest_shared_session' : 'stateless',
        intendedGuardFuture: $authDomain === 'customer' ? 'customer_guard' : 'merchant_guard',
        onboardingApplicable: false,
        actorId: null,
        routeOwnerAuthDomain: $authDomain,
        sessionId: $request->hasSession() ? $request->session()->getId() : null,
    );
}
```

### 4.2 Decision Tree

```
Input: Referer header (string) or Origin header (string fallback)
  ↓
Empty? (both Referer and Origin are null/empty)
  ├── Yes → routeDomain = 'merchant_users', authDomain = 'merchant', intendedGuardFuture = 'merchant_guard'
  └── No  → check str_contains(referer, '/storefront/account')
              ├── Yes → routeDomain = 'customer_account', authDomain = 'customer', intendedGuardFuture = 'customer_guard'
              └── No  → routeDomain = 'merchant_users', authDomain = 'merchant', intendedGuardFuture = 'merchant_guard'

Additional fields:
  actorType = null (always — CSRF is pre-auth)
  sessionOrigin = 'guest_shared_session' if session exists, 'stateless' if not
  onboardingApplicable = false (always)
  actorId = null (always)
```

### 4.3 Input Analysis

| Input | Source | Used? |
|---|---|---|
| `Referer` header | HTTP request header | **Primary input** — drives entire decision |
| `Origin` header | HTTP request header | **Fallback only** — used only if Referer is empty |
| Host/tenant | Request host, `X-Tenant-Id` header | **Not used** |
| Guard | Session, auth guard state | **Not used** |
| Session contents | `auth_domain` session key | **Not used** — `resolveForCsrf()` never checks session auth state |
| Auth state | Authenticated user | **Not used** — `actorType` hardcoded to null |
| Request path/route | URL path | **Not used** — all CSRF requests hit same URI |

### 4.4 Why Referer Is Required

The CSRF endpoint is called **before authentication** (there's no user, no token, no session identity). The only signal available to distinguish which domain initiated the request is the HTTP `Referer` header (or `Origin` as fallback). There is no session identity to check because the CSRF bootstrap happens to establish the session.

The complementary method `SessionOwnershipResolver::resolve()` (line 18-43) uses `IdentityContext` and `RouteDomainContext` — but those require an authenticated user and middleware annotation, neither of which exists at CSRF bootstrap time.

### 4.5 All Failure Modes for Referer-Based Ownership

| Scenario | Failure | Impact |
|---|---|---|
| **No Referer header** (direct API call, curl, Postman, Stripe webhook calling back to self, mobile app) | Defaults to `merchant_users` | Wrong domain assigned for customer-originated requests |
| **Referer stripped by privacy extension** (Brave, Firefox Enhanced Tracking Protection, uBlock Origin) | Defaults to `merchant_users` | Customer requests misclassified as merchant |
| **Referer stripped by meta referrer policy** (`<meta name="referrer" content="no-referrer">` on the page) | Defaults to `merchant_users` | Same as above |
| **No Referer after HSTS redirect** | Browser sent Referer as HTTP, server redirected to HTTPS, Referer lost in redirect | Defaults to `merchant_users` |
| **Cross-tab contamination** | Merchant tab opens storefront page → CSRF refresh from storefront tab includes merchant page Referer | Customer CSRF tagged as merchant |
| **Referer contains `/storefront/account` in URL but request is from merchant** | `str_contains` matches incorrectly | Merchant request tagged as customer |
| **Referer from non-standard path** | Market-specific URL like `/storefront/account/ar` still matches `str_contains` | Correctly identifies customer (but fragile — path-dependent) |
| **No Referer or Origin** (browser that doesn't send Origin, or fetch with `no-referrer` policy) | Empty string → defaults to merchant | Customer misclassified |
| **Nitro proxy doesn't forward Referer** (currently the case — see Section 2) | Laravel always receives empty Referer | **Always defaults to merchant** in production |

### 4.6 Critical Finding

**The `resolveForCsrf()` method is never called with a valid Referer in production.** The Nitro proxy's CSRF bootstrap call at `server/utils/api.ts:237` constructs a `headers` object that includes `Origin` (forwarded at line 219-222) but **does not forward `Referer`**. Additionally, even if it did, `resolveForCsrf()` defaults to checking `referer` first, and the CSRF call is server-to-server (Nitro proxy to Laravel), not browser-to-Laravel, so the browser's Referer would need to be explicitly forwarded. This means `resolveForCsrf()` always receives an empty (or Origin-only) input and always returns `merchant_users` / `merchant`.

The preparation controller's ownership inference is **always incorrect** in production because it never receives the browser's actual Referer.

## Section 5 — Ownership Model Discovery

### 5.1 Question: What Is the Intended CSRF Ownership Architecture?

**Answer: E. Multiple authorities** — CSRF will be owned per-guard (merchant, customer, platform), not by a single authority.

### 5.2 Evidence

**Evidence 1 — Wave 8 definition in debt roadmap**

`docs/wave6/transitional-authority-reduction.md:39`:
> "These routes cannot be fully isolated until the CSRF ownership model is finalized."

And at lines 87-92, Wave 8 is defined as:
> "Wave 8 | CSRF ownership finalization | -5 points"

This explicitly frames CSRF ownership as something to be "finalized" — implying it's currently **transitional/unowned** and needs to move to an owned state.

**Evidence 2 — CSRF isolation report**

`docs/auth/reports/csrf-isolation-report.md:27-28`:
> "Future guard split requires CSRF token verification against the *resolved* guard."

This states that CSRF verification must be guard-scoped, not global. Per-guard CSRF = multiple authorities.

**Evidence 3 — Guard split readiness scoring**

`tests/Feature/Auth/GuardSplitValidationScoringTest.php:36`:
```php
$this->assertContains('single_csrf_cookie_endpoint_still_shared', $analysis['unsupported_assumptions']);
```

The scoring system explicitly identifies "single CSRF cookie endpoint still shared" as an **unsupported assumption** for guard split — confirming the intended state is multiple CSRF endpoints or tokens.

**Evidence 4 — Browser coexistence report**

`docs/auth/reports/browser-coexistence-report.md:17`:
> "CSRF Refresh | Shared token. Valid for both domains. | Medium | Domain-specific headers in CSRF response"

The recommended mitigation is "domain-specific headers" — implying domain-scoped CSRF (per-authority), not global.

**Evidence 5 — Enforcement governance**

`docs/EXECUTION_GOVERNANCE.md`:
- Wave 3A (line 126): "cookie split" explicitly **forbidden**
- Wave 3B (line 163): "cookie split" explicitly **forbidden**
- Wave 3C (line 201): "cookie split" explicitly **forbidden**

Cookie/CSRF split was deferred out of Waves 3A-3C because the guard split entry criteria weren't met. The governance repeatedly defers it to a later wave (8), confirming it is the intended end state.

**Evidence 6 — Middleware naming**

The middleware parameter `identity.route:shared_transitional,{ownerAuthDomain},{enforcementMode}` takes an `ownerAuthDomain` parameter. For the CSRF route, this is `merchant` — acting as the **default fallback** owner. The intended state is an explicit owner domain, not `shared_transitional`.

**Evidence 7 — `CsrfOwnershipPreparationController` headers**

The response headers `X-Session-Auth-Domain` and `X-Future-Guard-Hint` are explicitly designed to communicate the resolved authority to the frontend. This infrastructure exists to support per-authority CSRF: the frontend would read these headers and know which authority the CSRF token belongs to.

**Evidence 8 — `TransitionalGuardResolver` guard mapping**

`docs/auth/governance/transitional-guard-resolution.md:20-25`:

| Auth Domain | Intended Guard |
|---|---|
| `merchant` | `merchant` |
| `customer` | `customer` |
| `platform` | `merchant` |
| unknown/shared transitional | `web` |

The `shared_transitional` → `web` mapping is explicitly temporary. The `web` guard is the undifferentiated shared state. The intended state is `merchant` and `customer` guards for their respective CSRF flows.

**Evidence 9 — CsrfCookieController placement in api.php**

The CSRF route is registered in `routes/api.php` (not `routes/web.php`) with the `api` prefix — implying it's an API infrastructure route, not a web page route. This is consistent with a guard-aware API architecture.

**Evidence 10 — No ADRs found**

Zero Architecture Decision Records exist for CSRF ownership. The architecture is documented only in governance docs, reports, and middleware code — no formal ADR supersedes the working assumption of per-domain CSRF.

### 5.3 Summary

| Source | Evidence | Supports |
|---|---|---|
| Debt roadmap | Wave 8 = "CSRF ownership finalization" | Multiple (transitional→owned) |
| CSRF isolation report | "token verification against resolved guard" | Multiple (per-guard) |
| Guard split scoring | "single CSRF endpoint" is unsupported assumption | Multiple (need multiple) |
| Browser coexistence | "domain-specific headers" as mitigation | Multiple (per-domain) |
| Execution governance | Cookie split forbidden in Waves 3A-3C | Multiple (deferred to later wave) |
| Middleware naming | `ownerAuthDomain=merchant` as transitional default | Multiple (explicit ownership coming) |
| Response headers | `X-Session-Auth-Domain` / `X-Future-Guard-Hint` | Multiple (authority communication) |
| Guard mapping | `shared_transitional` → `web` is temporary | Multiple (split into merchant/customer) |

Standard Laravel `Log::info()` — writes to the configured log channel. In development this is `stack` → `single` (`storage/logs/laravel.log`). In production this could be `stack` → `syslog`, `papertrail`, `slack`, etc. depending on deployment configuration.

### 6.3 Response Headers (Ephemeral — Not Stored)

| Header | Purpose |
|---|---|
| `X-Session-Auth-Domain` | Inferred domain for this CSRF refresh |
| `X-Session-Route-Domain` | Inferred route domain |
| `X-Future-Guard-Hint` | Guard that would own this in a split architecture |

These headers are returned in the HTTP response but are **not consumed** by any frontend code. They exist for observability and manual debugging.

### 6.4 Detected Violations / Conflicts

The `GuardShadowAnalyzer::analyze()` (Section 3.2) detects:

| Condition | Detection | Current Action |
|---|---|---|
| `ambiguousOwnershipPath` | Both merchant and customer resolvers would resolve | Logged but **never acted upon** |
| `guardMismatchAnomaly` | `authDomain` conflicts with shadow (e.g., authDomain=customer but merchant shadow resolves) | Logged but **never acted upon** |

### 6.5 Conflict Metrics

**There are zero conflict metrics.**

The telemetry is emitted but:
- No persistent storage of violations (no database table, no metric counter)
- No alerting threshold
- No dashboard visualization
- No aggregation or trending
- No automated analysis

The `session.csrf.ownership_traced` log events exist only as raw log lines. Any conflict analysis would require external log aggregation (Grafana, Datadog, Papertrail, etc.) querying for:
- `session_ownership.auth_domain != session_ownership.route_owner_auth_domain`
- `guard_shadow.ambiguous_ownership_path = true`
- `guard_shadow.guard_mismatch_anomaly = true`

### 6.6 Critical Finding — Telemetry Is Dead Code

Because the preparation controller is never called (see Section 2), **zero `session.csrf.ownership_traced` events are emitted in production**. The entire telemetry pipeline is unexercised. No violations are being detected because no ownership resolution is happening for CSRF requests.

## Section 8 — Enforcement Readiness

### 8.1 Overall Readiness Score: **15%**

| Stage | Score | Key Blocker |
|---|---|---|
| Stage 1 — Authority Discovery | ~30% | `resolveForCsrf()` works structurally but never receives valid input (no Referer forwarded). The preparation controller is dead code. |
| Stage 2 — Shadow Enforcement | ~10% | Telemetry is emitted but never consumed. No metrics, no alerts, no dashboards. `session.csrf.ownership_traced` goes to standard log output. |
| Stage 3 — Final Enforcement | ~0% | `shared_transitional` cannot be removed until per-domain CSRF exists. Cookie split was explicitly deferred from Waves 3A-3C. |

### 8.2 Stage 1 — Authority Discovery (30%)

**What it means**: The system can determine which authority domain owns a given CSRF request.

**What's in place**:
- `resolveForCsrf()` method exists with Referer/Origin heuristic
- `CsrfOwnershipPreparationController` exists as a wrapper
- Response headers communicate ownership

**Blocker**: The Nitro proxy does not forward the browser's Referer to Laravel's CSRF endpoint. `resolveForCsrf()` always receives empty input and defaults to `merchant`. The preparation controller is never called.

**What's needed**:
1. Forward `Referer` header from Nitro proxy to Laravel on CSRF bootstrap calls
2. Change the Nitro CSRF URL from `{apiRoot}` to `{apiBase}` so it hits the preparation controller instead of the plain Sanctum controller

### 8.3 Stage 2 — Shadow Enforcement (10%)

**What it means**: Ownership telemetry is emitted, collected, and analyzed to detect conflicts without enforcement.

**What's in place**:
- Telemetry logging infrastructure (`SessionGuardTelemetry::logCsrfOwnership`)
- `GuardShadowAnalyzer` for conflict detection
- Response headers for manual debugging

**Blocker**: Even after Stage 1 is fixed, telemetry goes to standard log output with no:
- Structured metrics (counters, gauges)
- Alerting thresholds
- Dashboard visualization
- Trend analysis (week-over-week, deployment-over-deployment)

**What's needed**:
- Add metric emission (e.g., Prometheus counter, StatsD gauge)
- Define thresholds for `ambiguousOwnershipPath` and `guardMismatchAnomaly`
- Create a runbook for ownership conflict investigation
- Collect baseline data for 1 week minimum before Stage 3

### 8.4 Stage 3 — Final Enforcement (0%)

**What it means**: CSRF tokens are scoped by authority domain and `shared_transitional` is removed from the CSRF route.

**Prerequisites**:

| # | Prerequisite | Blocked by | Risk if skipped |
|---|---|---|---|
| 1 | Per-domain CSRF tokens | Cookie split governance (forbidden in Waves 3A-3C) | Cross-domain CSRF token reuse |
| 2 | `CheckCsrfDomain` middleware | Not implemented | No enforcement mechanism |
| 3 | `shared_transitional` removal from CSRF route | Prerequisites 1-2 | 403 on every CSRF refresh |
| 4 | `TransitionalGuardResolver` exemption removal | Prerequisite 3 | `isFallback` throw on CSRF endpoint |
| 5 | Session tag validation (`csrf_auth_domain`) | Prerequisite 1-2 | No way to verify token domain match |

**Risks of Stage 3 without Stage 2 baseline**:
- No production data on how often Referer-based ownership is wrong
- No baseline for `ambiguousOwnershipPath` and `guardMismatchAnomaly` rates
- No ability to measure improvement or regression

### 9.4 Phase 3 — Per-Domain CSRF Enforcement

**Architecture**: Single endpoint with session-scoped domain tagging.

**Why not separate endpoints or cookie names**: Both conflict with `EXECUTION_GOVERNANCE.md` guard split entry criteria (cookie split forbidden until guard split is verified). Session tagging is reversible and does not require cookie naming changes.

**Implementation design**:

**Step 1 — Tag session with CSRF domain**

File: `app/Http/Controllers/Api/Shared/Auth/Preparation/CsrfOwnershipPreparationController.php`
```php
$ownership = $this->sessionOwnershipResolver->resolveForCsrf($request);
$request->session()->put('csrf_auth_domain', $ownership->authDomain);
```

Tags the session with the domain that initiated the CSRF refresh. Tag persists for session lifetime or until overwritten by a new CSRF refresh from a different domain.

**Step 2 — Create middleware**

New file: `app/Http/Middleware/CheckCsrfDomain.php`
- Applies to all state-changing requests (POST, PUT, PATCH, DELETE)
- Reads `csrf_auth_domain` from session
- Resolves request's authority domain from identity middleware
- Compares: mismatch → 419 with `AUTH_012`
- When behind feature flag `CSRF_DOMAIN_ENFORCE=false`: logs mismatch but does not throw

**Step 3 — Register middleware**

Add to `app/Http/Kernel.php` in the `api` middleware group (positioned after session middleware but before route handlers).

Exclude the CSRF endpoint itself (tagging must happen before validation).

**Step 4 — Feature flag**

```php
// config/auth.php
'csrf_domain_enforce' => env('CSRF_DOMAIN_ENFORCE', false),
```

Gate all enforcement behind this flag. When `false`: only logs. When `true`: throws 419 on mismatch.

**Step 5 — Add error code**

`app/Enums/ErrorCode.php`:
```php
case AUTH_012 = 'AUTH_012'; // CSRF domain mismatch
```

**Step 6 — Remove `shared_transitional` from CSRF route**

`routes/api.php:287-288`:
```php
// Before:
Route::get('/sanctum/csrf-cookie', [CsrfOwnershipPreparationController::class, 'show'])
    ->middleware(['web', 'identity.route:shared_transitional,merchant,observe']);

// After:
Route::get('/sanctum/csrf-cookie', [CsrfOwnershipPreparationController::class, 'show'])
    ->middleware(['web']);
```

**Step 7 — Update `TransitionalGuardResolver`**

`app/Services/Auth/TransitionalGuardResolver.php:23`:
```php
// Before:
$isFallback = $intendedGuard === 'web' && $context->routeDomain !== RouteDomainEnum::SHARED_TRANSITIONAL;

// After:
$isFallback = $intendedGuard === 'web';
```

Only after Step 6 is complete and deployed without incident.
